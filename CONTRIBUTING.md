# Разработка

`main` содержит проверенное состояние прототипа. Текущая разработка ведётся в
`dev`, отдельные изменения в `feat/*`, `fix/*` и `docs/*`. Для изменений создаётся
PR в `dev`, перенос проверенной версии в `main` выполняется отдельным PR.
Первичная публикация синхронизирует `main` и `dev`. Публикация кода не означает
публикацию обученной модели или готового видеоролика.

## Локальные проверки

```powershell
docker compose build tools
docker compose run --rm --entrypoint python tools -m unittest discover -s tests -v
node --test tests/test_review_ui.cjs
docker compose --profile gpu --profile research --profile review config --quiet
git diff --check
```

JavaScript-тесты используют встроенный `node:test`, без npm-зависимостей.
Проверки Python выполняются в том же tools-образе, который обрабатывает датасет.
GPU-распознавание проверяется локально с фиксированным аудионабором и весами.
Обычный GitHub-hosted runner не подтверждает совместимость CUDA или качество ASR.

Для изменения модели сохраняйте общий набор, настройки декодирования, revision
и SHA256 файлов. Не сравнивайте результаты на разных обрезках аудио. Дообучение
не использует validation или holdout. Отчёты по будущему train явно отмечаются
как диагностические.

## Что включать в PR

Опишите наблюдаемое поведение, изменение и выполненные проверки. Укажите
ограничения измерений, если меняется обработка аудио, таймкодов или метрик.
Изменения зависимостей обновляют lock-файл с хешами. Actions и базовые образы
закрепляются commit SHA и digest соответственно.

`local/`, записи, `.veg`, веса и подробная пользовательская разметка не входят
в Git или Docker build context. Используйте синтетические данные для тестов.
Не публикуйте аудиопримеры и реальные расшифровки в issue или CI artifacts.
